ESP32 Web Server & HTML LED Control

Direct embedded device control over a local Wi-Fi network using the ESP32 microcontroller as a standalone asynchronous HTTP web server serving a responsive web interface to toggle hardware GPIO states in real time.

01 · Station Overview

Objective & Problem Definition

One-Paragraph Summary

The objective of this assignment is to develop an autonomous embedded web server hosted directly inside an ESP32 microcontroller that provides a zero-latency, local-network browser dashboard for switching an electrical load (represented by a physical LED). By hosting the HTTP server on-chip, this solution resolves the problem of high-latency, internet-dependent, or costly cloud middleman architectures for localized appliance control, ensuring complete operational autonomy and offline resilience within a private Local Area Network (LAN).

The Engineering Problem Addressed

Conventional smart home gadgets often depend on external cloud servers just to turn on a light bulb in the same room. If the external internet connection drops or the vendor's cloud server undergoes downtime, the user loses physical control over their smart environment. Furthermore, routing simple localized switching requests through public WAN networks introduces unwanted latency (200ms–1500ms) and privacy concerns.

The Embedded Solution

By implementing an on-chip HTTP daemon on the ESP32 using the Arduino WebServer.h library, the ESP32 joins the local Wi-Fi access point, receives a dedicated IP address via DHCP, listens on TCP port 80, and streams an in-memory HTML5/CSS3 graphical control panel directly to any authenticated browser on the network.

02 · Technical Foundation

Core Concepts Explained

Technical concepts broken down in student engineering terminology.

ESP32 Web Server Concept

A software server process running inside the ESP32 firmware that binds to TCP Port 80. Instead of running on a high-power Linux server or Apache container, it runs on the ESP32’s Xtensa LX6 dual-core microarchitecture, listening for incoming TCP socket connections and parsing HTTP request headers.

Wi-Fi Client-Server Model

The browser acts as the HTTP Client, while the ESP32 acts as the HTTP Server. When the client navigates to http://<ESP32_IP>/, a 3-way TCP handshake occurs over 2.4GHz 802.11 b/g/n Wi-Fi, followed by an HTTP GET request requesting the root document.

Stateless HTTP & Command Routing

HTTP is inherently stateless. Commands are transmitted via distinct Uniform Resource Identifiers (URIs): /led/on and /led/off. The ESP32 router executes server.on("/led/on", handleLedOn), drives GPIO 2 high, and responds with a fresh HTML payload updating the UI toggle state.

03 · Architecture

System Design & Data Flow

Complete end-to-end request-response cycle and architectural topology.

─────── HTTP GET /led/on ───────►

GPIO 2 (LED + 330Ω)

Detailed Communication Sequence

  1. Wi-Fi Handshake: ESP32 connects to the AP with WPA2-PSK credentials and registers its IP on the local subnet.
  2. Page Request: Browser requests http://192.168.1.184/. ESP32 serves the HTML document with styled ON/OFF buttons.
  3. Command Dispatch: The user clicks "TURN ON". The browser dispatches an asynchronous HTTP GET request to /led/on.
  4. Hardware Actuation: ESP32 receives the request header, matches the route handler, and executes digitalWrite(LED_PIN, HIGH).
  5. State Acknowledgment: ESP32 sends an HTTP 200 OK header with a text/html response body confirming LED status.

Wiring & Pin Configuration

Circuit Analysis & Safe Operating Range

The forward voltage drop of the red indicator LED is \(V_f \approx 2.0\text{V}\). The ESP32 logic output is \(V_{cc} = 3.3\text{V}\).

I = (V_out - V_f) / R = (3.3V - 2.0V) / 330Ω = 1.3V / 330Ω ≈ 3.94 mA

Because the maximum continuous drain per ESP32 GPIO pin is rated at 12mA–20mA, drawing ~3.94mA guarantees long-term thermal safety for the ESP32 silicon while providing bright optical feedback.

06 · Firmware Code

Implementation Source Code

Fully tested, compilable ESP32 Arduino C++ firmware with route handlers and HTML generator.

C++ / Arduino (esp32_web_server.ino) 
#include <WiFi.h>
#include <WebServer.h>

// Network Credentials
const char* ssid     = "YOUR_WIFI_SSID";
const char* password = "YOUR_WIFI_PASSWORD";

// Hardware Pin Definitions
const int LED_PIN = 2; // Onboard LED / External Circuit on GPIO 2
bool ledState = false;

// Create WebServer listening on standard HTTP TCP port 80
WebServer server(80);

// Generate Responsive HTML5 Dashboard
String generateHtml() {
  String html = "<!DOCTYPE html><html lang='en'><head>";
  html += "<meta charset='UTF-8'><meta name='viewport' content='width=device-width, initial-scale=1.0'>";
  html += "<title>ESP32 LED Control</title>";
  html += "<style>";
  html += "body{font-family:'Segoe UI',sans-serif;background:#0d1117;color:#c9d1d9;text-align:center;padding:50px 20px;}";
  html += ".card{max-width:420px;margin:auto;background:#161b22;border:1px solid #30363d;border-radius:16px;padding:36px;box-shadow:0 10px 30px rgba(0,0,0,0.5);}";
  html += "h1{color:#58a6ff;font-size:24px;margin-bottom:6px;}";
  html += ".status{font-size:16px;margin:24px 0;font-weight:600;}";
  html += ".btn{display:inline-block;width:100%;padding:14px;font-size:16px;font-weight:bold;border-radius:10px;text-decoration:none;transition:0.2s;}";
  html += ".btn-on{background:#238636;color:white;} .btn-on:hover{background:#2ea043;}";
  html += ".btn-off{background:#da3633;color:white;} .btn-off:hover{background:#f85149;}";
  html += "</style></head><body>";
  html += "<div class='card'>";
  html += "<h1>ESP32 Web Server</h1>";
  html += "<p style='color:#8b949e;font-size:13px;'>Direct Local Embedded Control</p>";
  html += "<div class='status'>Current State: <span style='color:" + String(ledState ? "#3fb950" : "#f85149") + "'>" + (ledState ? "ON" : "OFF") + "</span></div>";
  if (ledState) {
    html += "<a class='btn btn-off' href='/led/off'>TURN LED OFF</a>";
  } else {
    html += "<a class='btn btn-on' href='/led/on'>TURN LED ON</a>";
  }
  html += "</div></body></html>";
  return html;
}

// Route Handlers
void handleRoot() {
  server.sendHeader("Cache-Control", "no-cache, no-store, must-revalidate");
  server.send(200, "text/html", generateHtml());
}

void handleLedOn() {
  ledState = true;
  digitalWrite(LED_PIN, HIGH);
  Serial.println("[HTTP] Route /led/on executed -> GPIO 2 HIGH");
  server.sendHeader("Location", "/");
  server.send(303); // Redirect back to root to refresh view
}

void handleLedOff() {
  ledState = false;
  digitalWrite(LED_PIN, LOW);
  Serial.println("[HTTP] Route /led/off executed -> GPIO 2 LOW");
  server.sendHeader("Location", "/");
  server.send(303); // Redirect back to root to refresh view
}

void handleNotFound() {
  server.send(404, "text/plain", "404: Endpoint Not Found on ESP32");
}

void setup() {
  Serial.begin(115200);
  pinMode(LED_PIN, OUTPUT);
  digitalWrite(LED_PIN, LOW);

  // Initialize Wi-Fi Connection
  Serial.print("Connecting to Wi-Fi SSID: ");
  Serial.println(ssid);
  WiFi.begin(ssid, password);

  while (WiFi.status() != WL_CONNECTED) {
    delay(500);
    Serial.print(".");
  }

  Serial.println("\n[Wi-Fi] Connected successfully!");
  Serial.print("[Wi-Fi] Assigned IP Address: ");
  Serial.println(WiFi.localIP());

  // Register Web Server Routes
  server.on("/", HTTP_GET, handleRoot);
  server.on("/led/on", HTTP_GET, handleLedOn);
  server.on("/led/off", HTTP_GET, handleLedOff);
  server.onNotFound(handleNotFound);

  // Start HTTP Daemon
  server.begin();
  Serial.println("[HTTP] WebServer started on port 80");
}

void loop() {
  // Listen and process incoming client connections
  server.handleClient();
}

Key Firmware Architecture Breakdown

  • server.handleClient(): Continuously polls the underlying TCP stack for incoming client packets without blocking delays.
  • HTTP 303 See Other Redirect: When /led/on is executed, sending a 303 redirect immediately commands the browser to issue a clean GET / request. This prevents duplicate command triggers if the user clicks reload.
  • Cache-Control Header: Forcing no-cache prevents mobile Chrome and Safari from serving stale cached states instead of asking the ESP32 for the live state.

09 · Engineering Journal

Challenges Encountered & Root-Cause Fixes

Documenting physical hardware and software failures encountered during station development.

BUG-01 ESP32 Wi-Fi Brownout Reset Loop Upon Transmission
✕ The Failure Observed

Whenever the ESP32 attempted to initialize Wi-Fi transmission in WiFi.begin(), the Serial Monitor outputted Brownout detector was triggered and continuously rebooted in an infinite crash loop.

Root Cause: The ESP32 2.4GHz RF radio draws short burst currents up to 350mA–450mA during Wi-Fi beacon association. The development board was plugged into an unpowered laptop USB 2.0 port that sagged below 4.5V, tripping the internal hardware Brownout Detector.

✓ The Engineering Fix

Connected a 100 µF electrolytic decoupling capacitor directly across the ESP32 3.3V and GND power rails on the breadboard to buffer transient RF current surges. Switched from laptop USB port to a regulated 5V 2.0A bench power supply. The brownout resets ceased permanently.

BUG-02 Mobile Browser Stale Cache & Out-of-Sync Toggle Button
✕ The Failure Observed

After toggling the LED once from a mobile smartphone browser, pressing the toggle button a second time failed to send a new request to the ESP32. The mobile browser showed the old LED state despite the physical hardware having changed.

Root Cause: Mobile Safari and Chrome aggressively cache HTTP GET responses from local IP addresses when caching headers are missing. Subsequent clicks loaded the cached HTML page from device memory instead of hitting the ESP32 socket.

✓ The Engineering Fix

Configured explicit HTTP response headers in the route handler: server.sendHeader("Cache-Control", "no-cache, no-store, must-revalidate"); and changed the response status from 200 to HTTP 303 (See Other) redirecting back to root. The browser was forced to re-fetch live hardware state on every click.
